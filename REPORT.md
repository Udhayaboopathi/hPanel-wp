# Own hPanel — Implementation Report

Built locally on 2026-10-31 in `~/workspace/own-hpanel-build` (git repo, branch `main`, not pushed — the push is handled separately). Go toolchain: go1.23.12 installed under `~/workspace/.tools/go`. **No connection of any kind was made to the production server (130.210.42.20)** — no SSH, no probing, no deployment. That server is referenced only as the default `SERVER_IP` value in DNS instructions, exactly as specified.

## Implemented features

- **Panel (`cmd/panel`)** — unprivileged web UI + API; never opens the Docker socket. Embedded Go templates + real vendored HTMX 2.0.4 (50,917 bytes, fetched from unpkg) + vanilla JS; light/dark themes.
- **Agent (`cmd/agent`)** — privileged provisioning worker on a Unix socket (`/run/own-hpanel/agent.sock`), bearer-token auth (constant-time compare, 0600 token file), allowlisted ops only (`CreateSite, DeleteSite, StartSite, StopSite, RestartSite, BackupSite, RestoreSite, WPCLI, ApplyConfig, RotateDBPassword, DBSize, Ping, Discovery, Stats, Logs`), full re-validation of every request, and a production guard refusing to mutate any container without `own-hpanel.managed=true`. The single permitted exception is connecting the panel's own `wordpress-mariadb` to a new per-site network (never stops/restarts/recreates it) plus read-only discovery.
- **Auth** — Argon2id (64 MiB/t3/p2), TOTP MFA (pquerna/otp), server-side sessions (SHA-256 token hashes, HttpOnly/SameSite=Lax, Secure in prod), CSRF on every authenticated POST, login rate limiting (10 fails/15 min, `login_attempts` table), single-use hashed recovery codes (use revokes all sessions + disables TOTP), logout-all, password change revoking sessions, audit log with secret redaction.
- **Store** — SQLite WAL via `modernc.org/sqlite` (pure Go, no CGO), embedded migration creating all 14 specified tables + recovery_codes/login_attempts, crash recovery marking `running` jobs `interrupted` at boot, bounded connections, sample pruning.
- **Provisioning** — durable DB-backed jobs (states + validated transitions, progress, events, attempts, cancel, retry, duplicate-create prevention, max 2 concurrent). WP admin password is held in panel memory only for the create job — never written to the DB. Per-site DB passwords are AES-256-GCM encrypted at rest.
- **Create Site flow (agent)** — validation → Traefik router/domain conflict scan → existing `redberyl-internal` network + shared MariaDB verification → per-site network → connect MariaDB → validated SQL provisioning (DB + least-privilege user, scoped grants only) → site dir + `.env` (0600) + compose from the approved template → container create (pinned `wordpress:6.7.2-php8.3-apache` / php8.2 variant, Traefik labels with unique router `own-hpanel-<siteid>`, `websecure` + `letsencrypt`, redirect-only `wpadmin.` alias, no published ports, 0.5 CPU/512 MB default Lightweight, 768 MB Standard, healthcheck, `no-new-privileges`, `cap_drop ALL`) → idempotent reuse on retry → WP-CLI install via one-shot `wordpress:cli-2.11.0-php8.3` helper container → DNS check distinguishing `ready` vs `dns_pending` (DNS failure is not a provisioning failure).
- **Management** — start/stop/restart/backup/restore (domain-typed delete confirmation; `RESTORE` confirmation), WP-CLI operations allowlist (version, updates, plugins/themes list/activate/deactivate/update, cache flush, checksums, admin password reset), DB password rotation, DNS/SSL check (real TLS dial + expiry + Cloudflare-range detection), domain change, lifecycle statuses in dashboard/list.
- **Editors** — env editor restricted to an approved key schema with masked secrets; YAML editor with double policy validation (panel + agent), diff preview before apply, version history and rollback. Policy rejects privileged, host net/PID/IPC, devices, published ports, Docker socket mounts, host binds outside the site dir, unapproved images, dangerous caps, missing ownership labels.
- **File manager** — per-site rooted browsing/view/edit/upload (streamed)/download/mkdir/rename/delete with `SafeJoin` traversal protection, sensitive-file hiding (`.env`, `wp-config.php`), DELETE confirmation.
- **Backups** — streaming tar.gz of files + `mariadb-dump` via one-shot client container, SHA-256 verification before a backup is marked ready, retention that never deletes the last verified backup, download, restore (files + DB import), stdlib SigV4 S3 PUT uploader for external destinations.
- **Monitoring** — real host CPU/RAM/disk/load from `/proc` + Statfs (5 s cache, bounded sample storage), per-container stats/logs via the agent when connected, honest "agent unavailable" states instead of invented numbers.
- **UI pages** — first-run setup (+ one-time recovery codes/TOTP secret), login, TOTP, recovery, dashboard (real metrics), websites (search/filter/sort/pagination), 3-step create wizard (server-validated preview, DNS records A @ and wpadmin → 130.210.42.20 with Copy button, generate/show-hide password), website detail with overview/env/yaml/files/wp/db/domain/backups/jobs/danger tabs, jobs list+detail, backups, monitoring, audit, account/security, settings, 404/error. Every button posts to a real endpoint.
- **Deployment artifacts** — multi-stage Dockerfile (panel/agent targets), root `compose.yaml` (panel + dedicated `wordpress-mariadb` MariaDB 11.4, tuned 256 M buffer pool/100 connections, no ports, Traefik-labelled panel on the external `redberyl-internal` network), `.env.example` (no secrets), Makefile, `deployment/install.sh` (read-only discovery first with before/after container snapshots; `--apply` gate; no destructive commands anywhere), agent systemd unit, README, SECURITY.md, docs/DEPLOYMENT.md, docs/RECOVERY.md.

## Known limitations (honest)

1. **Live WordPress creation was NOT tested against the production VPS or any Docker host** — this VM has no Docker and server access is explicitly out of scope for this phase. Docker integration tests exist but are build-tagged `integration` and excluded from default runs. The full create path (MariaDB connect, container create, WP-CLI install, Traefik routing, Let's Encrypt issuance) must be verified on a Docker host / at deployment time, following docs/DEPLOYMENT.md §4.
2. Pinned image tags (`wordpress:6.7.2-php8.3-apache`, `wordpress:cli-2.11.0-php8.3`, `mariadb:11.4`) should be re-verified against Docker Hub at deployment; if a tag differs, update `internal/security.ApprovedImages` and the agent constants together.
3. MariaDB provisioning runs through `mariadb` client exec / one-shot client containers (no direct MySQL protocol connection from the panel; the `go-sql-driver/mysql` dependency was therefore dropped by `go mod tidy` as unused).
4. Job progress events from the agent are returned in one batch at the end of an agent call (plus panel-side start/finish events) — not streamed live.
5. Backup reconciliation in the panel re-derives the artifact path from the backups-directory naming convention after the backup job succeeds and verifies it by streaming SHA-256; the agent already verified the artifact at creation.
6. Migration/import is supported via the backup-restore path (panel archive format: `files/…` + `db.sql`) and WP-CLI serialization-safe search-replace helpers (`internal/wordpress.SearchReplaceArgs`); a dedicated guided migration wizard UI and domain-change search-replace execution are not wired as one-click flows yet — domain change currently updates the panel record + admin alias and instructs the operator, with a cache-flush job queued.
7. TOTP setup shows the secret + otpauth URL as text (no QR image generation — no extra dependency was added for it).
8. S3 upload is implemented (stdlib SigV4) but scheduled/automatic S3 offloading and scheduled backups are settings-level only in v1; local backups are fully functional.
9. Single-administrator design (schema and audit support the admin ID throughout; RBAC roles are a future extension, as the spec allowed).
