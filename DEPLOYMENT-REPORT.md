## Deployment mechanism (unchanged)

Push to `main` triggers the self-hosted runner workflow: guard → checkout
→ protected snapshot → tests → build → `docker compose up -d
--force-recreate panel agent` (MariaDB and its volume are never recreated)
→ agent socket verification → panel health verification → protected
snapshot diff. No new ports, no new reverse proxy, no Traefik changes, no
`docker prune`. Existing production containers are not touched: the
application changes are confined to the `own-hpanel` and
`own-hpanel-agent` containers.

## Migration / compatibility notes

- No schema migration is required. Boot-time crash recovery now also
  reconciles stale `queued` jobs, `provisioning`/`deleting` websites and
  `creating` backups (see BUG-FIX-REPORT #11) — on first boot of the new
  build this runs against the production store and is a no-op unless such
  stale rows exist.
- TOTP seeds written by older builds are plaintext; the new code reads
  them transparently and all newly written seeds are encrypted. Existing
  recovery codes remain valid; newly generated ones are longer (80-bit).
- Session cookies are now `Secure` by default in code as they already
  were in the production compose — no behaviour change in production.
- The compose-policy validator is stricter; every existing site's stored
  configuration was generated by the same generator the new validator was
  tested against (`GenerateCompose` self-validates, and its output passes
  the new policy in the test suite).

## Access limitation (stated plainly)

The assistant has no direct access to the production server — by the
operator's standing instruction, deployment happens only through the
GitHub Actions self-hosted runner, and production inspection is via
operator-supplied output. This report therefore does not claim a live
post-deploy verification the assistant cannot perform.

## Post-deploy verification (operator steps)

1. Confirm the Actions run for this commit is green and the panel loads
   at https://hpanel.krwebsolution.com (healthy).
2. Open **Websites → wp-1c46776b (sudoinnovation.tech)**. Its status shows
   `failed`/`missing` and the new **Repair website** card appears.
3. In the repair form, enter a **new WordPress admin password** (≥12
   chars — the original was never stored, by design) and confirm. The
   repair job verifies the site's database (`wp_1c46776b_db`) and files
   exist, recreates only the container, and installs WordPress.
4. When the job succeeds, open the website and its wp-admin, then use
   **Restart** once on the now-existing container — it resolves by label
   and must succeed.
5. Optional spot-checks: a failed job's page shows its real (non-100%)
   progress; the monitoring page shows live per-container stats; the
   website page shows a non-zero database size.

## Rollback

The previous build is the parent commit (`1d31b06`). Reverting this
commit and pushing restores it through the same pipeline; the database
needs no rollback (no schema change; reconciliation writes only affect
stale rows, and encrypted TOTP seeds remain readable because pre-existing
rows were already accepted in both forms — note: seeds *created* by the
new build would not be readable by the old build; if a rollback happens
after regenerating a TOTP seed, disable/re-enable TOTP after rolling
back).
